# ADR-002 — Locked PDFs: built-in Android engine first, `@cantoo/pdf-lib` fallback for phones without unlock

- **Status:** Accepted (owner, 2026-10-17; self-check in `owner-decisions-2026-10-17.md`). The shopkeeper's phone tier is still unknown, so option (i) is built (build rule 5).
- **Spike:** (d). Evidence:
  - `docs/evidence/phase-0/2026-10-03/task9-locked-pdf-summary.md`
  - `instrumentation-all-*.txt`
  - `pdf-spike-*.txt`
  - `src/spikes/unlock-fallback.test.ts`

## Question

Can PrintSaathi open password-locked PDFs (e-Aadhaar) on every Android version it supports, **inside the isolated engine**, without weakening PLAN §B? And which phones need the fallback?

## Fixtures

The fixtures are synthetic: no personal data, user password `RAMA1965`, a 50 mm black square on page 1. They are generated by `tests/generate/make-locked-pdfs.mjs`.

| File | Encryption |
|---|---|
| `owner-only.pdf` | AES-256 R6, empty user password |
| `user-aes256.pdf` | AES-256 R6 (V5) |
| `user-aes128.pdf` | AES-128 (V4/R4) |
| `user-rc4.pdf` | RC4-128 (V2/R3) |
| `decrypted-*.pdf` | What option (i) produces |

pdf.js independently confirms each fixture: it needs the password, and opens with it.

## Results: built-in engine inside the isolated process (emulators)

| API | Tier (`pdfUnlockTier`) | Owner-only | User password + right password | Wrong password | Decrypted copy (option i) | Garbage |
|---|---|---|---|---|---|---|
| 24 (2 GB) | NONE | opens, renders ✓ | refused (password needed) → fallback | — | opens, renders ✓ | Damaged |
| 28 (2 GB) | NONE | opens, renders ✓ | fallback needed | — | opens, renders ✓ | Damaged |
| 30 (image without S-extension 13) | NONE | opens, renders ✓ | fallback needed | — | opens, renders ✓ | Damaged |
| 35 | NATIVE_35 | opens, renders ✓ | AES-256 / AES-128 / RC4: open + render ✓ | refused ✓ | ✓ | Damaged |
| 36 | NATIVE_35 | opens, renders ✓ | all three ✓ | refused ✓ | ✓ | Damaged |

"Renders" means page 1 was drawn onto white inside the isolated engine and dark ink was found (presence, not position). All rows come from the final regression, `docs/evidence/phase-0/2026-10-03/final-regression/` (26 passed on API 35 and 36; 23 passed + 3 honest skips on API 24, 28 and 30; 0 failed anywhere). **PdfRenderer works inside `isolatedProcess` on every tested level**, so PLAN §B holds for PDFs.

**Not observable here:** the PRE_V tier (API 30–34 with S-extension ≥ 13). The emulator images carry no Play system updates. A real API 31–34 phone is needed for it (user checklist).

## Results: option (i), `@cantoo/pdf-lib` 2.11.1 (Node)

- **Decryption:** AES-256, AES-128 and RC4-128 all decrypt with the right password and are refused with a wrong one.
- **Output:** the saved copy is unencrypted (`isEncrypted = false`), and pdf.js opens it with no password.
- **Requirements:** decryption needs no Web Crypto (only `encrypt()` does), so it works in any WebView ≥ 92.

## Decision (proposed)

1. **Always try the built-in engine first, with an empty password.** Owner-only files therefore open with no Unlock screen.
2. **NATIVE_35 and PRE_V phones:** unlock natively in the isolated engine, with no bridge exception.
3. **NONE phones:** option (i). This is the one documented bridge exception (PLAN §G5):
   - `@cantoo/pdf-lib` is lazy-loaded (about 222 KB gzip, only on the Unlock screen).
   - It decrypts in the WebView and sends the decrypted PDF (≤ 20 MB, 256 KB chunks) to `work/unlocked.pdf`.
   - The isolated engine opens it with its classic PdfRenderer (proven on API 24) and deletes it after printing.
4. **Option (ii), bundled PDFium, is not needed.** Option (i) handled every encryption type tested.
   - Revisit only if a real e-Aadhaar fails option (i) (user checklist §D).
   - Or if form fields and stamps must render on NONE phones (PLAN §G4 banner).
5. **Build rule (PLAN §G5 YAGNI):** if the shopkeeper's phone is NATIVE_35 or PRE_V, option (i) is not built in V1, and other phones show "This phone can't open locked PDFs…". If the shopkeeper's phone is NONE, or still unknown when Phase 7 starts, option (i) is built.

## Consequences

- One bounded bridge exception, only on NONE phones.
- The password stays in memory: in the engine binder call (native) or in the WebView (fallback). It is never stored or logged.
- **Weakest evidence:** emulators only, and no real e-Aadhaar yet. UIDAI's actual encryption parameters are unverified until the owner's own e-Aadhaar is tested (user checklist).
